Começando (fluxo com o agente)

Você não cria nada à mão — descreve, o agente constrói:

  1. Na sessão do agente, dentro da pasta do projeto, peça as telas: "quero as telas de login e cadastro do meu sistema, que abre num dashboard com lista de produtos" (ou digite /design).
  2. Na primeira vez o agente pergunta a marca (cor primária, estilo de fonte, tom) e cria o design/design-system.css + design-system.md. Todos os canvases seguintes reutilizam.
  3. O agente cria um canvas por fluxo (ex.: login/, dashboard/), valida tudo e devolve o link: http://localhost:8765/viewer.html?canvas=login.
  4. Abra o link, teste o sistema funcionando e comente o que quiser mudar (próxima seção). O agente ajusta e o visualizador recarrega sozinho.
Dica: comece por um fluxo pequeno e concreto. O ciclo inteiro (gerar → testar → comentar → ajustar) fica visível em minutos.

Comentar e iterar (o ciclo de revisão)

Comentário na tela inteira

  1. Selecione a tela (um clique) e clique 💬 Comentar esta tela.
  2. Escreva o pedido. O visualizador copia uma mensagem formatada — cole no chat do agente:
[Design: design/login › Login (01-login.html)] aumentar o espaçamento do formulário

Comentário em um elemento específico 🎯

  1. Clique 🎯 Elemento (o cursor vira mira; Esc sai).
  2. Passe o mouse: cada elemento ganha destaque com o seletor e um trecho do texto.
  3. Clique no elemento e escreva o ajuste. Ele vira um alfinete numerado na tela.
  4. Marque quantos quiser e mande tudo de uma vez com ⧉ Comentários (n):
[Design: design/login › Login (01-login.html) › body > main > form > button "Entrar"] deixar este botão em largura total

O agente localiza pelo seletor (depois pelo trecho) e edita só aquele ponto. Alfinetes têm × para remover e não aparecem no PNG exportado.

Ciclo completo: comente → cole no chat → agente edita → o visualizador atualiza sozinho. Sem sair do navegador.

Comentários persistentes (pins) 🎯

Regra dual-channel 🎯: cada comentário de elemento faz duas coisas de uma só vez: (1) grava um pin persistente — o alfinete numerado na tela, que sobrevive ao reload e aparece no painel ⧉ Comentários (n) — e (2) copia a mensagem de chat [Design: …] para você colar no agente. O pin é o registro persistente (status por elemento, painel de pendências, contagem na toolbar); a mensagem de chat é o canal que instrui o agente. O formato da mensagem de chat é inalterado — os pins são um canal a mais, nunca uma mudança de gramática.

Os pins vivem em design/comments.json, escrito somente pelo servidor (nunca edite à mão):

{
  "comments": [
    {
      "id": "p-1a2b3c4d5e6f",
      "canvas": "login",
      "file": "01-login.html",
      "selector": "body > main > form > button",
      "snippet": "Entrar",
      "rect": { "x": 12, "y": 340, "width": 120, "height": 44 },
      "status": "open",
      "replies": [ { "text": "deixar este botão em largura total", "createdAt": "2026-10-07T12:00:00.000Z" } ],
      "createdAt": "2026-10-07T12:00:00.000Z",
      "_demo": true
    }
  ]
}

Schema do pin: {id, canvas, file, selector?, snippet?, rect?, status, replies, createdAt, _demo?} — id gerado pelo servidor (p-<hex>); criação exige canvas+file; atualização é por id (status + replies, que são anexados). O texto do comentário é o primeiro item de replies (o pin não tem campo text); cada reply é {text, createdAt} (a forma legada at ainda é aceita na entrada e normalizada para createdAt). status vale "open" | "resolved" | "stale". _demo?: boolean é opcional — marca pins de demonstração (fixtures/exemplo) e só é persistido quando declarado explicitamente como true; qualquer outro tipo é recusado pela API (400).

Regra de staleness — escritores nomeados: o status stale tem exatamente dois escritores: node design/validate.mjs --mark-stale (a única escrita do validador — marca os pins cuja âncora sumiu da tela) e a API de revert (POST /api/revert, que marca os pins afetados pela restauração). Tentar escrever stale por qualquer outro caminho é recusado (400 invalid) — inclusive num POST comum de pin. No painel, pins stale aparecem destacados e não contam como pendência aberta. Em --share pins, painel e contagem ficam ocultos (ver API local).

Snapshots e comparação

Um snapshot congela o estado de um canvas como material de revisão: o painel Snapshots do visualizador (botão Salvar snapshot) grava design/snapshots/<canvas>/<label>/ com duas formas do mesmo estado:

  • src/ — a forma-fonte (o que o agente edita): as telas do canvas byte a byte (marcas de componente intactas), canvas.json, data.json, o tokens.json global e o components/ COMPLETO (registro + todos os partials).
  • render/ — a forma de apresentação: um HTML flat e autocontido por tela (CSS/JS/dados inline, zero ../), pronto para abrir em file:// e para a comparação A/B.

Cada snapshot tem um manifest.json (inventário de src/+render/ + tokensHash) que o revert valida antes de tocar em qualquer arquivo.

Comparar dois estados

Na mesma lista escolha os lados A e B (um snapshot ou o estado atual) e clique Comparar. São dois modos:

  • Lado a lado (padrão) — duas colunas com scroll sincronizado;
  • Onion skin — o lado B empilhado sobre o A em overlay, com a intensidade no controle input#opacity (0 = só o A, 1 = só o B).

Reverter para um snapshot

O botão "Reverter para este snapshot" (com passo de confirmação) chama POST /api/revert com {canvas, label} e restaura o src/ do snapshot em replace integral (nunca merge); depois roda sempre o pipeline node design/scripts/gen-tokens.mjs → node design/scripts/sync-components.mjs → node design/validate.mjs (exit 0 exigido) e marca como stale os pins cuja âncora sumiu. O visualizador copia então a mensagem de confirmação:

[Design-Reset: design/<canvas> — snapshot "<label>" restaurado]

Essa mensagem é apenas confirmação de estado: o agente não edita nada — reconhece e segue.

Limites do restore: o restore é replace integral por artefato de src/ — telas, canvas.json, data.json, tokens.json e components/ completo substituem integralmente os correspondentes na raiz servida, e arquivos fora de src/ sobrevivem intactos. Os globais (tokens.json, components/) voltam exatamente ao estado do snapshot e afetam os outros canvases: a unidade é o snapshot do canvas (o src/ inteiro), e o restore global de tokens/components é por replace integral.

Códigos do revert: 400 = manifest inválido ou dessincronizado, detectado ANTES do restore — a raiz fica intacta e nada foi restaurado; 500 = o pipeline falhou depois do restore, com rollback completo para o estado anterior; 404 = snapshot inexistente.

Modo fluxo (testar o sistema de verdade)

Duplo clique em uma tela abre o modo fluxo: a tela em tamanho real, interativa — você loga, navega, cadastra. A barra flutua no topo e sai da frente sozinha depois de alguns segundos sem mouse; qualquer movimento sobre a tela traz ela de volta. Na barra:

  • ◀ ▶ — volta e avança pelo histórico de navegação do fluxo.
  • ⟲ — reinicia o fluxo do começo (por tela).
  • 🎯 Elemento — liga o modo de comentar elemento dentro do modo fluxo, com a tela em tamanho cheio (o melhor lugar para isso).
  • 🌙 — alterna claro/escuro sem sair do fluxo.
  • ← Voltar — fecha o modo fluxo.

Um canvas pode navegar para outro (login → dashboard): o sistema inteiro é navegável, e o estado (quem logou, o que foi criado) atravessa os canvases. O botão ⟲ Reset fluxo da barra zera tudo.

Cenários de dados

O data.json de cada canvas pode ter cenários nomeados que sobrepõem os dados base — é como você valida estados sem tocar em código:

{
  "items": [ …dados padrão… ],
  "scenarios": {
    "vazio":   { "items": [] },
    "critico": { "items": [ { "qty": 0, … } ] }
  }
}

Selecione no visualizador e confira se cada cenário compõe bem (lista vazia, tudo abaixo do mínimo, falha de API). Trocar de cenário limpa o estado do fluxo — cada rodada começa limpa.

Como as telas ficam interativas

As telas incluem um runtime minúsculo e offline, o mock.js, dados fictícios em data.json e os estilos do runtime no mock.css (as telas linkam ../mock.css; o JavaScript só liga e desliga classes — ele nunca injeta CSS):

Transições entre telas

Cada tela pode declarar sua animação de entrada no canvas.json:

{ "id": "overview", "name": "Visão geral", "file": "01-overview.html", "device": "tablet", "transition": "fade" }

"transition" vale fade, slide-left ou none (padrão quando ausente; o validador rejeita qualquer outro valor com o código unknown-transition). Na navegação com Mock.go, a tela de destino ganha a classe mock-enter-fade/mock-enter-slide-left no <body>, que se remove sozinha em menos de 300 ms — o prefers-reduced-motion desliga a animação por completo. A classe é resolvida pelo nome do arquivo de destino no canvas.json do canvas atual: funciona nos saltos dentro do mesmo canvas (inclusive um self-nav como Mock.go('01-overview.html'), o padrão de "recarregar lista"), enquanto Mock.go('../dashboard/01-overview.html') (troca de canvas) é navegação simples, sem classe de entrada.

Scroll preservado

A posição de rolagem de cada tela é guardada em sessionStorage na chave scroll.<canvas>.<tela>: salva no Mock.go (e no pagehide, para navegações comuns) e restaurada quando a tela volta. As chaves scroll.* ficam fora do espaço mock.* de propósito — o "⟲ Reset fluxo" limpa só o estado mock.*, e o scroll sobrevive ao reset.

Fallback sem JS (e a regra do CSS)

O gatilho de um overlay é um link comum para a tela do modal — <a href="03-modal.html">Excluir conta</a>. Com JS, o clique abre a tela como camada modal; sem JS, o navegador segue o href e abre a própria tela do modal (que é uma tela completa e válida do canvas). Nada de markup duplicado na página hospedeira: a camada renderiza o <body> da própria tela. E todos os estilos do runtime vivem no mock.css — o JavaScript nunca injeta CSS, só alterna as classes .mock-toast, .mock-overlay, .mock-backdrop e .mock-enter-*.

Regras que o agente respeita: nada de CDN ou URL remota (ícones SVG inline, fontes do sistema), tokens do design system para toda cor/espaçamento, os dois temas sempre funcionando, e a tela continua compondo mesmo se o JavaScript falhar.

API local

Além de servir os arquivos, o serve.mjs expõe uma API de escrita em /api/* (comentários e snapshots) usada pelo visualizador. A raiz servida é ./design relativo ao diretório de onde o servidor é executado (mudança de comportamento — antes era a pasta do próprio script); é a mesma raiz que o pipeline (gen-tokens/sync-components/validate) usa.

Uso: node design/serve.mjs [porta] [--share] — porta padrão 8765, bind 127.0.0.1. No start o servidor imprime uma linha parseável URL: <base> TOKEN: <token>. Toda rota /api/* exige o header X-Design-Token com esse token da execução; o token é injetado no viewer.html por rewrite em memória (o placeholder window.__DESIGN_TOKEN__ = null do arquivo em disco fica intacto).

Hardening somente em /api/* (as rotas estáticas nunca são interceptadas — servir em LAN continua possível): Host precisa ser localhost/127.0.0.1 (porta ignorada); Origin presente e cross-site → 403 (ausente = permitido); campos canvas, label e id seguem ^[a-z0-9-]+$; valor com cara de traversal (.., /, \) → 403; corpo acima de 256 KB → 413. Erros respondem JSON {"error": código}.

MétodoPathBodyRespostaCódigos
GET/api/comments— { comments: [pin, …] } — pin: {id, canvas, file, selector?, snippet?, rect?, status, replies, createdAt, _demo?}; status = "open"|"resolved"|"stale"; replies = [{text, createdAt}] (a forma legada at é normalizada na entrada). Persistido em design/comments.json — schema completo em Comentários persistentes 200; 400 (comments.json inválido); 403 (sem token, Host/Origin)
POST/api/comments pin {id?, canvas?, file?, selector?, snippet?, rect?, status?, replies?, _demo?} — cria (exige canvas+file) ou atualiza (por id: status + replies, que são anexados) { comments: [...] } (lista atualizada) 200; 400 (schema/corpo malformado; escrita de stale — recusada: os únicos escritores de stale são validate.mjs --mark-stale e a API de revert, ver Comentários persistentes); 403 (sem token, Host/Origin, traversal); 404 (canvas/arquivo inexistente); 413
GET/api/snapshots— { snapshots: [{canvas, label, date}] } (lista por canvas — alimenta a lista do visualizador) 200; 403 (sem token, Host/Origin)
POST/api/snapshot{canvas, label} { snapshot: {canvas, label, date} } — grava snapshots/<canvas>/<label>/{src, render, manifest.json} (src/ = forma-fonte: telas do canvas + tokens.json + components/ COMPLETO; render/ = flat autocontido por tela; manifest.json = {label, date, inventory:{src,render}, tokensHash}) 200; 400 (schema); 403 (sem token, Host/Origin, traversal); 404 (canvas inexistente); 409 (label duplicado); 413; 500 (falha de escrita + rollback do diretório)
POST/api/revert {canvas, label} { reverted: {canvas, label}, pipeline: {gen, sync, validate} } — restaura o src/ do snapshot em replace integral (unidade = snapshot do canvas, ver Snapshots e comparação), roda sempre gen-tokens → sync-components → validate e marca stale os pins afetados 200; 400 (corpo inválido; manifest inválido/dessincronizado — detectado ANTES de qualquer restore, raiz intacta); 403 (sem token, Host/Origin, traversal); 404 (snapshot inexistente); 413; 500 (falha de escrita/pipeline + rollback completo)

Códigos de erro JSON (taxonomia pinada, corpo {"error": código}): invalid (400), forbidden e traversal (403), not-found (404), duplicate (409), too-large (413), internal (500) — sucesso é 200 com o corpo JSON documentado na tabela. O GET /api/snapshots ignora manifestos inválidos ou dessincronizados na listagem — a validação completa (schema + inventário contra os arquivos em disco) acontece no revert. Com --share o bind vira 0.0.0.0 (preview em LAN) e toda rota /api/* responde 403 (leituras incluídas — nada vaza).

Changelog (w4): o bind padrão do servidor passou a ser 127.0.0.1 (só a própria máquina) — a API de escrita nunca fica exposta na rede. Para testar no celular ou em outro aparelho da LAN, --share é o caminho de migração: node design/serve.mjs 8766 --share (bind 0.0.0.0). Em --share o visualizador entra em modo leitura com degradação declarada: além do 403 em toda rota /api/*, ele esconde as ações de escrita e os recursos alimentados por /api (pins nas telas, painel de pendências, responder/resolver) e mostra o banner "modo leitura — comentários e snapshots indisponíveis". O contrato vale para o futuro: as UIs de snapshots/comparação (que chegam depois) também precisam ficar ocultas em --share — marcá-las com data-share-hide no HTML já basta, pois o visualizador as esconde via syncShareDegradation().

Design tokens e utilitários

O tokens.json é a fonte única de todos os tokens do design system (claro e escuro). A partir dele o gerador escreve dois arquivos gerados, que nunca se edita à mão: design-system.css (as variáveis var(--…)) e utilities.css (o vocabulário fechado de utilitários). Depois de qualquer mudança em tokens.json, regenere os dois:

node design/scripts/gen-tokens.mjs

A matriz de utilitários tem 140 entradas exatas (137 classes + 3 helpers [data-state=…]), cobrindo estas famílias:

Componentes

As telas reutilizam instâncias de componentes vindas de design/components/ (o registro components.json mais um partial por componente). Uma instância nunca é markup solto de componente: é o partial embrulhado por um par de marcadores, com três argumentos obrigatórios (os únicos aceitos):

<!-- component:button size=md tone=primary state=default -->…<!-- /component:button -->

Os valores precisam estar nos enums do registro: size vale sm|md|lg, tone vale primary|ghost e state vale default|hover|active|disabled. Os espaços preenchíveis (slots) são pares de marcadores dentro da região, e o conteúdo entre eles é preservado byte a byte:

<!-- slot:label -->Entrar<!-- /slot:label -->

Precedência: marker-args-win

Os argumentos do marcador são a fonte de verdade da variante. A cada sincronização a região é rematerializada a partir do partial: data-size, data-tone, data-state e as classes de variante da raiz são re-emitidos a partir do marcador. O conteúdo dos slots e atributos data-* extras que você colocar na raiz sobrevivem intactos.

Sincronizar: sync e --check

Depois de editar um partial em design/components/ (ou os argumentos de um marcador), rode antes de apresentar qualquer tela:

node design/scripts/sync-components.mjs

Com --check o comando vira dry-run: mostra um diff arquivo:linha de cada região divergente, termina com código 1 se houver divergência e 0 se estiver tudo limpo, e nunca grava nada. O validador também aplica as regras de componente em qualquer .html não isento (independente do canvas.json) com os códigos component-unknown, component-variant, component-marker, component-divergence e slot-marker.

Exemplo: mudar a variante do Button

Instrução recebida: "mudar a variante do Button". O caminho documentado é editar o marcador e rodar o sync, sem reescrever markup à mão:

  1. Na tela, localize o marcador do botão e troque o argumento no próprio marcador (ex.: size=md vira size=lg): <!-- component:button size=lg tone=primary state=default -->…
  2. Rode node design/scripts/sync-components.mjs: a instância ganha data-size="lg" e as classes de variante de lg (o marcador vence).
  3. Valide antes de apresentar: node design/validate.mjs design/<canvas>.
Fonte única: no pacote, example/components/ é cópia byte-idêntica de assets/components/. Os partials se editam só na fonte única; a cópia do exemplo é referência, nunca alvo de edição.

Regressão checklist

Checklist executável de regressão do design pack - o mesmo que o agente roda depois de mudanças no runtime, no viewer ou na instalação. Cada item tem nome e id estável (data-check) e traz o assert exato; os itens marcados (navegador) exigem o visualizador aberto (manual ou Playwright) e os demais rodam em node puro, sem navegador. Um item falho trava a entrega.

  1. Mock.data/state/go/toast - carregue design/mock.js num node:vm com DOM/sessionStorage stub e asserte: await Mock.data('items') devolve os itens do data.json do canvas; Mock.state.set('user', .) → Mock.state.get('user') devolve o valor, persiste em sessionStorage sob mock. e Mock.state.clear() zera; Mock.go('02-cadastro.html') grava location.href preservando ?scenario= e guardando o scroll da tela atual; Mock.toast('Salvo!', 2200) cria #mock-toast.mock-toast.show com o texto e remove .show após o tempo.
  2. Cenários ?scenario= - com location.search='?scenario=vazio': Mock.scenario() → 'vazio' e await Mock.data('items') → [] (o override do data.json vence a base); sem parâmetro Mock.scenario() → '' e valem os dados base.
  3. Export PNG (navegador) - 📷 PNG da tela gera uma URL data:image/png com length > 0 (prévia + download); o code path é htmlToImage.toPng sobre vendor/html-to-image.js.
