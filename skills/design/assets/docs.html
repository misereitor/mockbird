Getting started (the agent flow)

You don't build anything by hand — you describe, the agent builds:

  1. In the agent session, inside the project folder, ask for the screens: "I want the login and sign-up screens of my system, opening into a dashboard with a product list" (or type /design).
  2. The first time the agent asks about the brand (primary color, font style, tone) and creates design/design-system.css + design-system.md. Every later canvas reuses them.
  3. The agent creates one canvas per flow (e.g. login/, dashboard/), validates everything and returns the link: http://localhost:8765/viewer.html?canvas=login.
  4. Open the link, test the working system and comment whatever you want changed (next section). The agent adjusts and the viewer reloads by itself.
Tip: start with a small, concrete flow. The whole cycle (generate → test → comment → adjust) becomes visible in minutes.

Commenting and iterating (the review cycle)

Comment on the whole screen

  1. Select the screen (one click) and click 💬 Comment this screen.
  2. Write the request. The comment is saved — nothing is sent yet; you pick it in the 💬 Pending outbox and send whenever you want:
[Design: design/login › Login (01-login.html)] increase the form spacing

Comment on a specific element 🎯

  1. Click 🎯 Element (the cursor becomes a crosshair; Esc leaves).
  2. Hover: every element gets highlighted with its selector and a text snippet.
  3. Click the element and write the adjustment. It becomes a numbered pin on the screen.
  4. Mark as many as you want and send them all at once with ⧉ Comments (n):
[Design: design/login › Login (01-login.html) › body > main > form > button "Entrar"] make this button full width

The agent locates the element by selector (then by snippet) and edits only that spot. Pins have × to remove and never appear in the exported PNG.

Full cycle: comment → paste into chat → agent edits → the viewer updates by itself. Without leaving the browser.

Persistent comments (pins) 🎯

Dual-channel rule 🎯: every element comment does two things at once: (1) writes a persistent pin — the numbered pin on the screen, which survives reload and shows up in the ⧉ Comments (n) panel — and (2) prepares the [Design: …] chat message in the 💬 Pending outbox — you check which comments to send and hit 🚀 Send selected. A review modal opens where you can add a note; delivery happens only when you click 🚀 Send to the agent — straight into your OpenCode session (the clipboard copy remains as the fallback when the agent is unreachable — the overlay always shows which one happened). Every comment can also be deleted, replied to, resolved and reopened from the same panel. A comment belongs to the exact surface where it was created: made inside a popup/modal, it attaches to that overlay and disappears with it — never floating fixed on the screen below. The panel is organized in tabs (Pending · Resolved) with a text filter, and selected comments go away at once with Delete selected. In the comment box Enter saves; Ctrl+Enter or Shift+Enter breaks a line. The pin is the persistent record (status per element, pending panel, toolbar count); the chat message is the channel that instructs the agent. The chat message format is unchanged — pins are one extra channel, never a grammar change.

Pins live in design/comments.json, written only by the server (never edit it by hand):

{
  "comments": [
    {
      "id": "p-1a2b3c4d5e6f",
      "canvas": "login",
      "file": "01-login.html",
      "selector": "body > main > form > button",
      "snippet": "Entrar",
      "rect": { "x": 12, "y": 340, "width": 120, "height": 44 },
      "status": "open",
      "replies": [ { "text": "make this button full width", "createdAt": "2026-10-07T12:00:00.000Z" } ],
      "createdAt": "2026-10-07T12:00:00.000Z",
      "_demo": true
    }
  ]
}

Pin schema: {id, canvas, file, selector?, snippet?, rect?, status, replies, createdAt, _demo?} — id generated by the server (p-<hex>); creation requires canvas+file; updates go by id (status + replies, which are appended). The comment text is the first item of replies (the pin has no text field); each reply is {text, createdAt} (the legacy at form is still accepted on input and normalized to createdAt). status is "open" | "resolved" | "stale". _demo?: boolean is optional — it marks demo pins (fixtures/example) and is only persisted when explicitly declared as true; any other type is refused by the API (400).

Staleness rule — named writers: the stale status has exactly two writers: node design/validate.mjs --mark-stale (the validator's only write — marks the pins whose anchor vanished from the screen) and the revert API (POST /api/revert, which marks the pins affected by the restore). Writing stale through any other path is refused (400 invalid) — even in a regular pin POST. In the panel, stale pins are highlighted and do not count as open pending. Under --share pins, the panel and the count stay hidden (see Local API).

Snapshots and comparison

A snapshot freezes a canvas state as review material: the viewer's Snapshots panel (Save snapshot button) writes design/snapshots/<canvas>/<label>/ with two forms of the same state:

  • src/ — the source form (what the agent edits): the canvas screens byte by byte (component markers intact), canvas.json, data.json, the global tokens.json and the COMPLETE components/ (registry + every partial).
  • render/ — the presentation form: one flat, self-contained HTML per screen (inline CSS/JS/data, zero ../), ready to open via file:// and for A/B comparison.

Each snapshot has a manifest.json (inventory of src/+render/ + tokensHash) that revert validates before touching any file.

Comparing two states

In the same list pick sides A and B (a snapshot or the current state) and click Compare. There are two modes:

  • Side by side (default) — two columns with synced scrolling;
  • Onion skin — side B stacked over A in an overlay, with intensity on the input#opacity control (0 = only A, 1 = only B).

Both sides also accept live screens of the canvas ("Screens in this canvas" group) — comparing two screens side by side, not just snapshot states.

Reverting to a snapshot

The "Revert to this snapshot" button (with a confirmation step) calls POST /api/revert with {canvas, label} and restores the snapshot's src/ as a full replace (never a merge); then it always runs the pipeline node design/scripts/gen-tokens.mjs → node design/scripts/sync-components.mjs → node design/validate.mjs (exit 0 required) and marks as stale the pins whose anchor vanished. The viewer then copies the confirmation message:

[Design-Reset: design/<canvas> — snapshot "<label>" restored]

This message is state confirmation only: the agent edits nothing — it acknowledges and moves on.

Restore limits: the restore is a full replace per src/ artifact — screens, canvas.json, data.json, tokens.json and the complete components/ fully replace their counterparts in the served root, and files outside src/ survive untouched. The globals (tokens.json, components/) return exactly to the snapshot state and affect the other canvases: the unit is the canvas snapshot (the whole src/), and the global tokens/components restore is a full replace.

Revert codes: 400 = invalid or desynced manifest, detected BEFORE the restore — the root stays intact and nothing was restored; 500 = the pipeline failed after the restore, with a full rollback to the previous state; 404 = snapshot not found.

Rescue: per-file history

While the server runs, every change to any file in design/ is recorded as a revision (design/.history/, the newest 20 per file). The 🕘 History panel lists a file's revisions and restores exactly one — one file, one version, nothing else in the system is touched (screens are independent; shared files restore as a whole, and the view refreshes by itself). Coverage starts when the server starts; each restore is itself recorded as a new revision.

Flow mode (test the system for real)

Double-click a screen to open flow mode: the screen at full size, interactive — you log in, navigate, create records. The bar floats at the top and gets out of the way by itself after a few seconds without mouse movement; any movement over the screen brings it back. On the bar:

  • ◀ ▶ — back and forth through the flow's navigation history.
  • ⟳ — reload the current screen, keeping the flow position (⟲ Reset flow on the main bar starts the whole flow over).
  • 🎯 Element — turns on element-comment mode inside flow mode, with the screen full size (the best place for it).
  • 🌙 — toggles light/dark without leaving the flow.
  • ← Back — closes flow mode.

A canvas can navigate into another (login → dashboard): the whole system is navigable, and state (who logged in, what was created) crosses canvases. The ⟲ Reset flow button on the bar resets everything.

Data scenarios

Each canvas's data.json can hold named scenarios that override the base data — that's how you validate states without touching code:

{
  "items": [ …default data… ],
  "scenarios": {
    "empty":    { "items": [] },
    "critical": { "items": [ { "qty": 0, … } ] }
  }
}

Pick one in the viewer and check that each scenario composes well (empty list, everything under the minimum, API failure). Switching scenarios clears the flow state — every round starts clean.

How the screens become interactive

The screens include a tiny offline runtime, mock.js, fictitious data in data.json and the runtime styles in mock.css (the screens link ../mock.css; the JavaScript only toggles classes — it never injects CSS):

Mock API

APIWhat it does
await Mock.data('items')Reads the canvas's data.json data (with the chosen scenario applied).
Mock.state (.set('user', …), .get('user'), .clear())Flow state shared across the whole project (login in one canvas, read in another). .clear() zeroes it — that's what the viewer's "⟲ Reset flow" calls.
Mock.go('03-detalhe.html')Navigates to another flow screen — even in another canvas: Mock.go('../dashboard/01-overview.html'). Preserves ?scenario= and saves the current screen's scroll position.
Mock.toast('Saved!')Visual feedback for a simulated action.
Mock.overlay('03-modal.html')Opens a canvas screen as a modal layer: renders the screen's content over a backdrop, traps focus inside the layer, Esc closes the top layer and a backdrop click closes it when dismissible (default true). A missing file becomes an error toast, no layer.
Mock.close()Closes the top modal layer; focus returns to the element that opened it.
Mock.scenario()Returns the active scenario from ?scenario= (empty string on base data) — use it to branch content per scenario.

Navigation vs overlay: a plain screen link (<a href="03-modal.html">) always opens an overlay (modals, details). For real navigation — sidebar, menus, tabs — put data-go="02-screen.html" on the item and keep the same href as the JS-off fallback: the runtime routes data-go to Mock.go, so ?scenario= and the enter transition are preserved. Items can cross canvases too: data-go="../dashboard/01-overview.html".

Transitions between screens

Each screen can declare its enter animation in canvas.json:

{ "id": "overview", "name": "Overview", "file": "01-overview.html", "device": "tablet", "transition": "fade" }

"transition" is fade, slide-left or none (the default when absent; the validator rejects any other value with the unknown-transition code). When navigating with Mock.go, the target screen gets the mock-enter-fade/mock-enter-slide-left class on <body>, which removes itself in under 300 ms — prefers-reduced-motion disables the animation entirely. The class is resolved by the target file name in the canvas.json of the current canvas: it works for hops inside the same canvas (including a self-nav like Mock.go('01-overview.html'), the "reload list" pattern), while Mock.go('../dashboard/01-overview.html') (canvas switch) is plain navigation with no enter class.

Preserved scroll

Each screen's scroll position is kept in sessionStorage under the scroll.<canvas>.<screen> key: saved on Mock.go (and on pagehide, for plain navigations) and restored when the screen returns. The scroll.* keys deliberately stay outside the mock.* namespace — "⟲ Reset flow" clears only mock.* state, and scroll survives the reset.

No-JS fallback (and the CSS rule)

An overlay trigger is a plain link to the modal screen — <a href="03-modal.html">Delete account</a>. With JS, the click opens the screen as a modal layer; without JS, the browser follows the href and opens the modal screen itself (which is a complete, valid canvas screen). No duplicated markup on the host page: the layer renders the screen's own <body>. And every runtime style lives in mock.css — the JavaScript never injects CSS, only toggles the .mock-toast, .mock-overlay, .mock-backdrop and .mock-enter-* classes.

Rules the agent respects: no CDN or remote URL (inline SVG icons, system fonts), design system tokens for every color/spacing, both themes always working, and the screen keeps composing even if JavaScript fails.

canvas.json defines order and size: device is mobile (390×844), tablet (834×1112) or desktop (1440×900), with optional width/height; each screen's enter transition is declared there too ("transition": "fade"|"slide-left"|"none" — see the mock API), and the optional "group" field clusters the screens into titled blocks in the viewer (complex projects stay readable).

Local API

Besides serving files, serve.mjs exposes a write API at /api/* (comments and snapshots) used by the viewer. The served root is ./design relative to the directory the server runs from (behavior change — it used to be the script's own folder); it is the same root the pipeline (gen-tokens/sync-components/validate) uses.

Usage: node design/serve.mjs [port] [--share] [--open[=canvas]] [--no-open] — default port 8765, bind 127.0.0.1. On start the server prints one parseable line URL: <base> TOKEN: <token>, and opens your default browser at the viewer (--open=<canvas> lands straight on a canvas, --no-open suppresses it, the BROWSER env var picks a specific browser; without flags it only opens from an interactive terminal). Every /api/* route requires the X-Design-Token header with that run's token; the token is injected into viewer.html by an in-memory rewrite (the window.__DESIGN_TOKEN__ = null placeholder in the file on disk stays intact).

Edit + preview at the same time: run two instances on different ports from the same project — node design/serve.mjs for you (full editing: comments, snapshots, history) and node design/serve.mjs 8766 --share for the network (read-only). The share startup prints a ready-to-paste LAN: URL; viewers see your edits live, and only the editing instance writes to disk (history included).

Hardening applies only to /api/* (static routes are never intercepted — LAN serving stays possible): Host must be localhost/127.0.0.1 (port ignored); a present cross-site Origin → 403 (absent = allowed); canvas, label and id fields follow ^[a-z0-9-]+$; a traversal-looking value (.., /, \) → 403; bodies over 256 KB → 413. Errors answer JSON {"error": code}.

MethodPathBodyResponseCodes

JSON error codes (pinned taxonomy, body {"error": code}): invalid (400), forbidden and traversal (403), not-found (404), duplicate (409), too-large (413), internal (500), agent-unavailable (502) — success is 200 with the JSON body documented in the table. GET /api/snapshots ignores invalid or desynced manifests in the listing — full validation (schema + inventory against the files on disk) happens at revert. With --share the bind becomes 0.0.0.0 (LAN preview) and every /api/* route answers 403 (reads included — nothing leaks).

Changelog (w4): the server's default bind became 127.0.0.1 (this machine only) — the write API is never exposed on the network. To test on a phone or another LAN device, --share is the migration path: node design/serve.mjs 8766 --share (bind 0.0.0.0). Under --share the viewer enters read-only mode with declared degradation: besides the 403 on every /api/* route, it hides write actions and /api-fed features (pins on screens, pending panel, reply/resolve) and shows the banner "read-only mode — comments and snapshots unavailable". The contract holds for the future: snapshot/comparison UIs must also stay hidden under --share — marking them with data-share-hide in the HTML is enough, since the viewer hides them via syncShareDegradation().

Design tokens and utilities

tokens.json is the single source of every design system token (light and dark). From it the generator writes two generated files, never edited by hand: design-system.css (the var(--…) variables) and utilities.css (the closed utility vocabulary). After any change to tokens.json, regenerate both:

node design/scripts/gen-tokens.mjs

For interchange with other tools there is a pure W3C/DTCG export — only groups, $type and $value, without the pack's extensions. The result is tokens.w3c.json, a derived artifact (never edit it by hand; regenerate when needed):

node design/scripts/export-tokens.mjs

The utility matrix has 140 exact entries (137 classes + 3 [data-state=…] helpers), covering these families:

Banned classes: the Tailwind palette (bg-zinc-900) and arbitrary values (text-[13px]). The vocabulary is closed and every color comes from the tokens.

Components

The screens reuse component instances from design/components/ (the components.json registry plus one partial per component). An instance is never loose component markup: it is the partial wrapped by a pair of markers, with three mandatory arguments (the only accepted ones):

<!-- component:button size=md tone=primary state=default -->…<!-- /component:button -->

The values must come from the registry enums: size is sm|md|lg, tone is primary|ghost and state is default|hover|active|disabled. Fillable spaces (slots) are marker pairs inside the region, and the content between them is preserved byte by byte:

<!-- slot:label -->Enter<!-- /slot:label -->

Precedence: marker-args-win

The marker arguments are the source of truth for the variant. On every sync the region is rematerialized from the partial: data-size, data-tone, data-state and the root variant classes are re-emitted from the marker. The slot content and any extra data-* attributes you put on the root survive intact.

Sync: sync and --check

After editing a partial in design/components/ (or a marker's arguments), run this before showing any screen:

node design/scripts/sync-components.mjs

With --check the command becomes a dry run: it prints a file:line diff of each divergent region, exits with code 1 if there is divergence and 0 when clean, and never writes. The validator also applies the component rules to any non-exempt .html (regardless of canvas.json) with the codes component-unknown, component-variant, component-marker, component-divergence and slot-marker.

Example: changing the Button variant

Instruction received: "change the Button variant". The documented path is editing the marker and running the sync, never rewriting markup by hand:

  1. On the screen, find the button marker and change the argument on the marker itself (e.g. size=md becomes size=lg): <!-- component:button size=lg tone=primary state=default -->…
  2. Run node design/scripts/sync-components.mjs: the instance gets data-size="lg" and the lg variant classes (the marker wins).
  3. Validate before showing: node design/validate.mjs design/<canvas>.
Single source: in the pack, example/components/ is a byte-identical copy of assets/components/. Partials are edited only at the single source; the example copy is a reference, never an edit target.

Regression checklist

An executable Mockbird regression checklist — the same one the agent runs after changes to the runtime, the viewer or the install. Each item has a stable name and id (data-check) and carries the exact assert; items marked (browser) need the viewer open (manual or Playwright) and the rest run in pure node, no browser. A failing item blocks delivery.

  1. Mock.data/state/go/toast - load design/mock.js in a node:vm with a DOM/sessionStorage stub and assert: await Mock.data('items') returns the data.json items; Mock.state.set('user', .) → Mock.state.get('user') returns the value, persists in sessionStorage under mock. and Mock.state.clear() zeroes it; Mock.go('02-cadastro.html') writes location.href preserving ?scenario= and saving the current screen's scroll; Mock.toast('Saved!', 2200) creates #mock-toast.mock-toast.show with the text and removes .show after the time.
  2. Scenarios ?scenario= - with location.search='?scenario=empty': Mock.scenario() → 'empty' and await Mock.data('items') → [] (the data.json override beats the base); with no parameter Mock.scenario() → '' and the base data applies.
  3. Export PNG (browser) - ⬇ Screen PNG produces a data:image/png URL with length > 0 (preview + download); the code path is htmlToImage.toPng over vendor/html-to-image.js.
  4. 🎯 message format - the copied message matches the viewer's literal template: whole screen [Design: design/<canvas> › <name> (<file>)]; element = › <selector> "<snippet>" appended to the bracket (persisted pins use the same template).
  5. Theme/device (browser) - the light/dark theme applies data-theme inside every screen; Device forces Phone 390×844/Tablet 834×1112/Desktop 1440×900 and Original respects each screen's size.
  6. Cross-canvas - Mock.go('../dashboard/01-overview.html') navigates to the other canvas with ?scenario= preserved; Mock.state written in one canvas is read in the other (login → dashboard → logout).
  7. Install smoke - node install.mjs --dir <tmp> → exit 0 and a present file inventory: <tmp>/design/SKILL.md, <tmp>/design/assets/docs.html, <tmp>/design/scripts/validate.mjs, <tmp>/impeccable/scripts/impeccable.cmd.
How to run: the node asserts (mock-api, scenarios, message, cross-canvas, install smoke) run in a harness that loads mock.js in a vm and checks the viewer + example; the (browser) items are the manual/Playwright step. Ask "run the regression" in the agent session to execute the whole checklist.

Troubleshooting

  • "The canvas X does not exist here yet" — the canvas is created by the agent along with the screens: ask for the screens in the project session. Also check that the server is running in the project's design/ folder and that the name in the URL (?canvas=…) is right.
  • Port 8765 busy — start on another one: node design/serve.mjs 8766 and adjust the link.
  • The bar doesn't show 🎯 / ⟲ / ⏺ — the project's viewer.html is outdated; copy the current version from the skill (ask the agent: "update the design/ files with the skill version").
  • Red problems banner — click to expand: each line says the code and the file. Fix it (or have the agent fix it) and reload.
  • Weird preferences — scenario/theme/device are per canvas in the browser; clearing the site data resets them.

Começando (fluxo com o agente)

Você não cria nada à mão — descreve, o agente constrói:

  1. Na sessão do agente, dentro da pasta do projeto, peça as telas: "quero as telas de login e cadastro do meu sistema, que abre num dashboard com lista de produtos" (ou digite /design).
  2. Na primeira vez o agente pergunta a marca (cor primária, estilo de fonte, tom) e cria o design/design-system.css + design-system.md. Todos os canvases seguintes reutilizam.
  3. O agente cria um canvas por fluxo (ex.: login/, dashboard/), valida tudo e devolve o link: http://localhost:8765/viewer.html?canvas=login.
  4. Abra o link, teste o sistema funcionando e comente o que quiser mudar (próxima seção). O agente ajusta e o visualizador recarrega sozinho.
Dica: comece por um fluxo pequeno e concreto. O ciclo inteiro (gerar → testar → comentar → ajustar) fica visível em minutos.

Comentar e iterar (o ciclo de revisão)

Comentário na tela inteira

  1. Selecione a tela (um clique) e clique 💬 Comentar esta tela.
  2. Escreva o pedido. O comentário é salvo — nada é enviado ainda; você o marca no painel 💬 Pendentes (caixa de saída) e envia quando quiser:
[Design: design/login › Login (01-login.html)] aumentar o espaçamento do formulário

Comentário em um elemento específico 🎯

  1. Clique 🎯 Elemento (o cursor vira mira; Esc sai).
  2. Passe o mouse: cada elemento ganha destaque com o seletor e um trecho do texto.
  3. Clique no elemento e escreva o ajuste. Ele vira um alfinete numerado na tela.
  4. Marque quantos quiser e mande tudo de uma vez com ⧉ Comentários (n):
[Design: design/login › Login (01-login.html) › body > main > form > button "Entrar"] deixar este botão em largura total

O agente localiza pelo seletor (depois pelo trecho) e edita só aquele ponto. Alfinetes têm × para remover e não aparecem no PNG exportado.

Ciclo completo: comente → cole no chat → agente edita → o visualizador atualiza sozinho. Sem sair do navegador.

Comentários persistentes (pins) 🎯

Regra dual-channel 🎯: cada comentário de elemento faz duas coisas de uma só vez: (1) grava um pin persistente — o alfinete numerado na tela, que sobrevive ao reload e aparece no painel ⧉ Comentários (n) — e (2) prepara a mensagem de chat [Design: …] na caixa de saída 💬 Pendentes — você marca quais comentários enviar e clica em 🚀 Enviar selecionados. Abre um modal de revisão onde você acrescenta uma observação; o envio só acontece quando você clica em 🚀 Enviar ao agente — direto para a sua sessão do OpenCode (a cópia para a área de transferência fica como fallback quando o agente está inalcançável — o overlay mostra sempre qual dos dois aconteceu). Todo comentário também pode ser excluído, respondido, resolvido e reaberto pelo mesmo painel. O comentário pertence à superfície exata onde foi criado: feito dentro de um popup/modal, ele se amarra àquele overlay e desaparece junto com ele — nunca ficando fixo na tela de baixo. O painel se organiza em abas (Pendentes · Resolvidos) com filtro por texto, e comentários selecionados somem de uma vez com Excluir selecionados. Na caixa de comentário Enter salva; Ctrl+Enter ou Shift+Enter quebra linha. O pin é o registro persistente (status por elemento, painel de pendências, contagem na toolbar); a mensagem de chat é o canal que instrui o agente. O formato da mensagem de chat é inalterado — os pins são um canal a mais, nunca uma mudança de gramática.

Os pins vivem em design/comments.json, escrito somente pelo servidor (nunca edite à mão):

{
  "comments": [
    {
      "id": "p-1a2b3c4d5e6f",
      "canvas": "login",
      "file": "01-login.html",
      "selector": "body > main > form > button",
      "snippet": "Entrar",
      "rect": { "x": 12, "y": 340, "width": 120, "height": 44 },
      "status": "open",
      "replies": [ { "text": "deixar este botão em largura total", "createdAt": "2026-10-07T12:00:00.000Z" } ],
      "createdAt": "2026-10-07T12:00:00.000Z",
      "_demo": true
    }
  ]
}

Schema do pin: {id, canvas, file, selector?, snippet?, rect?, status, replies, createdAt, _demo?} — id gerado pelo servidor (p-<hex>); criação exige canvas+file; atualização é por id (status + replies, que são anexados). O texto do comentário é o primeiro item de replies (o pin não tem campo text); cada reply é {text, createdAt} (a forma legada at ainda é aceita na entrada e normalizada para createdAt). status vale "open" | "resolved" | "stale". _demo?: boolean é opcional — marca pins de demonstração (fixtures/exemplo) e só é persistido quando declarado explicitamente como true; qualquer outro tipo é recusado pela API (400).

Regra de staleness — escritores nomeados: o status stale tem exatamente dois escritores: node design/validate.mjs --mark-stale (a única escrita do validador — marca os pins cuja âncora sumiu da tela) e a API de revert (POST /api/revert, que marca os pins afetados pela restauração). Tentar escrever stale por qualquer outro caminho é recusado (400 invalid) — inclusive num POST comum de pin. No painel, pins stale aparecem destacados e não contam como pendência aberta. Em --share pins, painel e contagem ficam ocultos (ver API local).

Snapshots e comparação

Um snapshot congela o estado de um canvas como material de revisão: o painel Snapshots do visualizador (botão Salvar snapshot) grava design/snapshots/<canvas>/<label>/ com duas formas do mesmo estado:

  • src/ — a forma-fonte (o que o agente edita): as telas do canvas byte a byte (marcas de componente intactas), canvas.json, data.json, o tokens.json global e o components/ COMPLETO (registro + todos os partials).
  • render/ — a forma de apresentação: um HTML flat e autocontido por tela (CSS/JS/dados inline, zero ../), pronto para abrir em file:// e para a comparação A/B.

Cada snapshot tem um manifest.json (inventário de src/+render/ + tokensHash) que o revert valida antes de tocar em qualquer arquivo.

Comparar dois estados

Na mesma lista escolha os lados A e B (um snapshot ou o estado atual) e clique Comparar. São dois modos:

  • Lado a lado (padrão) — duas colunas com scroll sincronizado;
  • Onion skin — o lado B empilhado sobre o A em overlay, com a intensidade no controle input#opacity (0 = só o A, 1 = só o B).

Os dois lados também aceitam telas vivas do canvas (grupo "Telas deste canvas") — comparar duas telas lado a lado, não só estados de snapshot.

Reverter para um snapshot

O botão "Reverter para este snapshot" (com passo de confirmação) chama POST /api/revert com {canvas, label} e restaura o src/ do snapshot em replace integral (nunca merge); depois roda sempre o pipeline node design/scripts/gen-tokens.mjs → node design/scripts/sync-components.mjs → node design/validate.mjs (exit 0 exigido) e marca como stale os pins cuja âncora sumiu. O visualizador copia então a mensagem de confirmação:

[Design-Reset: design/<canvas> — snapshot "<label>" restaurado]

Essa mensagem é apenas confirmação de estado: o agente não edita nada — reconhece e segue.

Limites do restore: o restore é replace integral por artefato de src/ — telas, canvas.json, data.json, tokens.json e components/ completo substituem integralmente os correspondentes na raiz servida, e arquivos fora de src/ sobrevivem intactos. Os globais (tokens.json, components/) voltam exatamente ao estado do snapshot e afetam os outros canvases: a unidade é o snapshot do canvas (o src/ inteiro), e o restore global de tokens/components é por replace integral.

Códigos do revert: 400 = manifest inválido ou dessincronizado, detectado ANTES do restore — a raiz fica intacta e nada foi restaurado; 500 = o pipeline falhou depois do restore, com rollback completo para o estado anterior; 404 = snapshot inexistente.

Resgate: histórico por arquivo

Enquanto o servidor roda, toda mudança em qualquer arquivo de design/ é registrada como uma revisão (design/.history/, as 20 mais recentes por arquivo). O painel 🕘 Histórico lista as revisões de um arquivo e restaura exatamente uma — um arquivo, uma versão, nada mais no sistema é tocado (as telas são independentes; arquivos compartilhados restauram por inteiro, e a visualização atualiza sozinha). A cobertura começa quando o servidor inicia; cada restauração também vira uma nova revisão.

Modo fluxo (testar o sistema de verdade)

Duplo clique em uma tela abre o modo fluxo: a tela em tamanho real, interativa — você loga, navega, cadastra. A barra flutua no topo e sai da frente sozinha depois de alguns segundos sem mouse; qualquer movimento sobre a tela traz ela de volta. Na barra:

  • ◀ ▶ — volta e avança pelo histórico de navegação do fluxo.
  • ⟳ — recarrega a tela atual, mantendo a posição do fluxo (⟲ Reset fluxo na barra principal reinicia o fluxo inteiro).
  • 🎯 Elemento — liga o modo de comentar elemento dentro do modo fluxo, com a tela em tamanho cheio (o melhor lugar para isso).
  • 🌙 — alterna claro/escuro sem sair do fluxo.
  • ← Voltar — fecha o modo fluxo.

Um canvas pode navegar para outro (login → dashboard): o sistema inteiro é navegável, e o estado (quem logou, o que foi criado) atravessa os canvases. O botão ⟲ Reset fluxo da barra zera tudo.

Como as telas ficam interativas

As telas incluem um runtime minúsculo e offline, o mock.js, dados fictícios em data.json e os estilos do runtime no mock.css (as telas linkam ../mock.css; o JavaScript só liga e desliga classes — ele nunca injeta CSS):

Navegação vs overlay: um link comum de tela (<a href="03-modal.html">) sempre abre um overlay (modais, detalhes). Para navegação de verdade — sidebar, menus, abas — ponha data-go="02-tela.html" no item e mantenha o mesmo href como fallback sem JS: o runtime encaminha o data-go para Mock.go, preservando ?scenario= e a transição de entrada. Itens também podem cruzar canvases: data-go="../dashboard/01-overview.html".

Transições entre telas

Cada tela pode declarar sua animação de entrada no canvas.json:

{ "id": "overview", "name": "Visão geral", "file": "01-overview.html", "device": "tablet", "transition": "fade" }

"transition" vale fade, slide-left ou none (padrão quando ausente; o validador rejeita qualquer outro valor com o código unknown-transition). Na navegação com Mock.go, a tela de destino ganha a classe mock-enter-fade/mock-enter-slide-left no <body>, que se remove sozinha em menos de 300 ms — o prefers-reduced-motion desliga a animação por completo. A classe é resolvida pelo nome do arquivo de destino no canvas.json do canvas atual: funciona nos saltos dentro do mesmo canvas (inclusive um self-nav como Mock.go('01-overview.html'), o padrão de "recarregar lista"), enquanto Mock.go('../dashboard/01-overview.html') (troca de canvas) é navegação simples, sem classe de entrada.

Scroll preservado

A posição de rolagem de cada tela é guardada em sessionStorage na chave scroll.<canvas>.<tela>: salva no Mock.go (e no pagehide, para navegações comuns) e restaurada quando a tela volta. As chaves scroll.* ficam fora do espaço mock.* de propósito — o "⟲ Reset fluxo" limpa só o estado mock.*, e o scroll sobrevive ao reset.

Fallback sem JS (e a regra do CSS)

O gatilho de um overlay é um link comum para a tela do modal — <a href="03-modal.html">Excluir conta</a>. Com JS, o clique abre a tela como camada modal; sem JS, o navegador segue o href e abre a própria tela do modal (que é uma tela completa e válida do canvas). Nada de markup duplicado na página hospedeira: a camada renderiza o <body> da própria tela. E todos os estilos do runtime vivem no mock.css — o JavaScript nunca injeta CSS, só alterna as classes .mock-toast, .mock-overlay, .mock-backdrop e .mock-enter-*.

Regras que o agente respeita: nada de CDN ou URL remota (ícones SVG inline, fontes do sistema), tokens do design system para toda cor/espaçamento, os dois temas sempre funcionando, e a tela continua compondo mesmo se o JavaScript falhar.

API local

Além de servir os arquivos, o serve.mjs expõe uma API de escrita em /api/* (comentários e snapshots) usada pelo visualizador. A raiz servida é ./design relativo ao diretório de onde o servidor é executado (mudança de comportamento — antes era a pasta do próprio script); é a mesma raiz que o pipeline (gen-tokens/sync-components/validate) usa.

Uso: node design/serve.mjs [porta] [--share] [--open[=canvas]] [--no-open] — porta padrão 8765, bind 127.0.0.1. No start o servidor imprime uma linha parseável URL: <base> TOKEN: <token> e abre o navegador padrão no viewer (--open=<canvas> cai direto num canvas, --no-open suprime, a env BROWSER escolhe um navegador específico; sem flags só abre de terminal interativo). Toda rota /api/* exige o header X-Design-Token com esse token da execução; o token é injetado no viewer.html por rewrite em memória (o placeholder window.__DESIGN_TOKEN__ = null do arquivo em disco fica intacto).

Editar + pré-visualizar ao mesmo tempo: suba duas instâncias em portas diferentes a partir do mesmo projeto — node design/serve.mjs para você (edição completa: comentários, snapshots, histórico) e node design/serve.mjs 8766 --share para a rede (somente leitura). O start do share imprime uma URL LAN: pronta para colar; quem vê acompanha suas edições ao vivo, e só a instância de edição grava em disco (histórico incluído).

Hardening somente em /api/* (as rotas estáticas nunca são interceptadas — servir em LAN continua possível): Host precisa ser localhost/127.0.0.1 (porta ignorada); Origin presente e cross-site → 403 (ausente = permitido); campos canvas, label e id seguem ^[a-z0-9-]+$; valor com cara de traversal (.., /, \) → 403; corpo acima de 256 KB → 413. Erros respondem JSON {"error": código}.

Códigos de erro JSON (taxonomia pinada, corpo {"error": código}): invalid (400), forbidden e traversal (403), not-found (404), duplicate (409), too-large (413), internal (500), agent-unavailable (502) — sucesso é 200 com o corpo JSON documentado na tabela. O GET /api/snapshots ignora manifestos inválidos ou dessincronizados na listagem — a validação completa (schema + inventário contra os arquivos em disco) acontece no revert. Com --share o bind vira 0.0.0.0 (preview em LAN) e toda rota /api/* responde 403 (leituras incluídas — nada vaza).

Changelog (w4): o bind padrão do servidor passou a ser 127.0.0.1 (só a própria máquina) — a API de escrita nunca fica exposta na rede. Para testar no celular ou em outro aparelho da LAN, --share é o caminho de migração: node design/serve.mjs 8766 --share (bind 0.0.0.0). Em --share o visualizador entra em modo leitura com degradação declarada: além do 403 em toda rota /api/*, ele esconde as ações de escrita e os recursos alimentados por /api (pins nas telas, painel de pendências, responder/resolver) e mostra o banner "modo leitura — comentários e snapshots indisponíveis". O contrato vale para o futuro: as UIs de snapshots/comparação (que chegam depois) também precisam ficar ocultas em --share — marcá-las com data-share-hide no HTML já basta, pois o visualizador as esconde via syncShareDegradation().

Design tokens e utilitários

O tokens.json é a fonte única de todos os tokens do design system (claro e escuro). A partir dele o gerador escreve dois arquivos gerados, que nunca se edita à mão: design-system.css (as variáveis var(--…)) e utilities.css (o vocabulário fechado de utilitários). Depois de qualquer mudança em tokens.json, regenere os dois:

node design/scripts/gen-tokens.mjs

Para intercâmbio com outras ferramentas existe o export W3C/DTCG puro — só grupos, $type e $value, sem as extensões do pack. O resultado é tokens.w3c.json, um artefato derivado (nunca se edita à mão; regenere quando precisar):

node design/scripts/export-tokens.mjs

Componentes

As telas reutilizam instâncias de componentes vindas de design/components/ (o registro components.json mais um partial por componente). Uma instância nunca é markup solto de componente: é o partial embrulhado por um par de marcadores, com três argumentos obrigatórios (os únicos aceitos):

<!-- component:button size=md tone=primary state=default -->…<!-- /component:button -->

Os valores precisam estar nos enums do registro: size vale sm|md|lg, tone vale primary|ghost e state vale default|hover|active|disabled. Os espaços preenchíveis (slots) são pares de marcadores dentro da região, e o conteúdo entre eles é preservado byte a byte:

<!-- slot:label -->Entrar<!-- /slot:label -->

Precedência: marker-args-win

Os argumentos do marcador são a fonte de verdade da variante. A cada sincronização a região é rematerializada a partir do partial: data-size, data-tone, data-state e as classes de variante da raiz são re-emitidos a partir do marcador. O conteúdo dos slots e atributos data-* extras que você colocar na raiz sobrevivem intactos.

Sincronizar: sync e --check

Depois de editar um partial em design/components/ (ou os argumentos de um marcador), rode antes de apresentar qualquer tela:

node design/scripts/sync-components.mjs

Com --check o comando vira dry-run: mostra um diff arquivo:linha de cada região divergente, termina com código 1 se houver divergência e 0 se estiver tudo limpo, e nunca grava nada. O validador também aplica as regras de componente em qualquer .html não isento (independente do canvas.json) com os códigos component-unknown, component-variant, component-marker, component-divergence e slot-marker.

Exemplo: mudar a variante do Button

Instrução recebida: "mudar a variante do Button". O caminho documentado é editar o marcador e rodar o sync, sem reescrever markup à mão:

  1. Na tela, localize o marcador do botão e troque o argumento no próprio marcador (ex.: size=md vira size=lg): <!-- component:button size=lg tone=primary state=default -->…
  2. Rode node design/scripts/sync-components.mjs: a instância ganha data-size="lg" e as classes de variante de lg (o marcador vence).
  3. Valide antes de apresentar: node design/validate.mjs design/<canvas>.
Fonte única: no pacote, example/components/ é cópia byte-idêntica de assets/components/. Os partials se editam só na fonte única; a cópia do exemplo é referência, nunca alvo de edição.

Regressão checklist

Checklist executável de regressão do Mockbird - o mesmo que o agente roda depois de mudanças no runtime, no viewer ou na instalação. Cada item tem nome e id estável (data-check) e traz o assert exato; os itens marcados (navegador) exigem o visualizador aberto (manual ou Playwright) e os demais rodam em node puro, sem navegador. Um item falho trava a entrega.

  1. Mock.data/state/go/toast - carregue design/mock.js num node:vm com DOM/sessionStorage stub e asserte: await Mock.data('items') devolve os itens do data.json do canvas; Mock.state.set('user', .) → Mock.state.get('user') devolve o valor, persiste em sessionStorage sob mock. e Mock.state.clear() zera; Mock.go('02-cadastro.html') grava location.href preservando ?scenario= e guardando o scroll da tela atual; Mock.toast('Salvo!', 2200) cria #mock-toast.mock-toast.show com o texto e remove .show após o tempo.
  2. Cenários ?scenario= - com location.search='?scenario=vazio': Mock.scenario() → 'vazio' e await Mock.data('items') → [] (o override do data.json vence a base); sem parâmetro Mock.scenario() → '' e valem os dados base.
  3. Export PNG (navegador) - 📷 PNG da tela gera uma URL data:image/png com length > 0 (prévia + download); o code path é htmlToImage.toPng sobre vendor/html-to-image.js.
  4. 🎯 formato da mensagem - a mensagem copiada casa o template literal do viewer: tela inteira [Design: design/<canvas> › <name> (<file>)]; elemento = › <selector> "<snippet>" acrescentado ao bracket (pins persistidos usam o mesmo template).
  5. Tema/dispositivo (navegador) - 🎛 Tema claro/escuro aplica data-theme dentro de todas as telas; Dispositivo força Celular 390×844/Tablet 834×1112/Desktop 1440×900 e Original respeita o tamanho de cada tela.
  6. Cross-canvas - Mock.go('../dashboard/01-overview.html') navega para o outro canvas com ?scenario= preservado; o Mock.state gravado num canvas é lido no outro (login → dashboard → logout).
  7. Install smoke - node install.mjs --dir <tmp> → exit 0 e inventário de arquivos presente: <tmp>/design/SKILL.md, <tmp>/design/assets/docs.html, <tmp>/design/scripts/validate.mjs, <tmp>/impeccable/scripts/impeccable.cmd.
Como rodar: os asserts de node (mock-api, cenários, mensagem, cross-canvas, install smoke) rodam num harness que carrega o mock.js num vm e confere viewer + exemplo; os itens (navegador) são o passo manual/Playwright. Peça "rode a regressão" na sessão do agente para executar o checklist inteiro.

Solução de problemas

  • "O canvas X ainda não existe aqui" — o canvas é criado pelo agente junto com as telas: peça as telas na sessão do projeto. Confira também se o servidor está rodando na pasta design/ do projeto e se o nome na URL (?canvas=…) está certo.
  • Porta 8765 ocupada — suba em outra: node design/serve.mjs 8766 e ajuste o link.
  • A barra não mostra 🎯 / ⟲ / ⏺ — o viewer.html do projeto está desatualizado; copie a versão atual da skill (pedir ao agente: "atualize os arquivos do design/ com a versão da skill").
  • Banner vermelho de problemas — clique para expandir: cada linha diz o código e o arquivo. Corrija (ou mande o agente corrigir) e recarregue.
  • Preferências esquisitas — cenário/tema/dispositivo ficam por canvas no navegador; limpar os dados do site reseta.
